# Testing and release

## 1. Test strategy

The system has no runtime dependencies and no server. Its test strategy is therefore built around:

1. **Pure helper tests** — audit, snapshots, task statistics, validation, CSV/ICS, state hash.
2. **Data integrity checks** — counts, required fields, statuses, links, budget totals.
3. **Static syntax checks** — every browser and Node script parses.
4. **Artifact consistency** — canonical state hash and generated files are current and tracked.
5. **Documentation checks** — required docs exist and internal links resolve.
6. **Browser smoke tests** — the gate, routes, management actions, reload persistence and console.
7. **Live checks** — the Pages origin and required assets answer after deployment.

## 2. Commands

| Command | What it verifies |
| --- | --- |
| `npm test` | 11 unit tests for management helpers and state hash |
| `npm run check` | Source data counts, IDs, statuses, links, budget totals |
| `npm run docs:check` | Required documentation and internal Markdown links |
| `npm run build:artifacts` | Regenerates briefs, go/no-go record and evidence CSV |
| `npm run gate` | Tracked state/artifacts + brief state hash + stale check |
| `npm run live:check` | Live Pages page and required static assets |
| `node --check <file>` | JavaScript syntax check |
| `node tools/serve.js 4173` | Local static preview |

The CI workflow is the authoritative automation. A local pass is necessary but not sufficient if the
change has not been pushed and checked on the runner.

## 3. Unit tests

`tests/management.test.js` covers:

- `ensure()` adds missing collections without overwriting existing data;
- audit attribution and entry shape;
- snapshot create/restore while preserving audit and snapshot history;
- task statistics and overdue detection;
- health counts, including default decision IDs;
- validation of acceptable state and rejection of unsupported statuses;
- CSV and ICS machine-readable output.

`tests/state-hash.test.js` covers:

- key-order independence;
- export-timestamp independence;
- value-change sensitivity;
- inclusion of `gonoArchive`.

Commands run with Node’s built-in test runner. No test dependency is installed.

## 4. Data integrity checks

`tools/check-data.js` loads the browser data scripts in a Node `global.window` shim and checks:

- 12 partners and 7 pilot cities;
- 22 + 27 = 49 compliance controls across 7 frameworks;
- 22 risks with 1–5 likelihood/impact values and valid statuses;
- 12 deliverables with valid due months and statuses;
- 19 first-90-days actions;
- 8 gates and 34 gate items with bilingual requirements and blocking flags;
- 6 decisions, 10 documents, 14 KPIs;
- WP3 total of €285,000 and 19 PM;
- unique IDs;
- gate/control/risk links where present.

A failed data check is a release blocker. Fix the source data rather than weakening the assertion.

## 5. Documentation checks

`npm run docs:check`:

- requires `AGENTS.md`, the documentation index, architecture, data model, workflows, operations,
  security, testing/release, incident/recovery, RACI and glossary documents;
- checks that each required document exists and is non-trivial;
- checks relative Markdown links and image paths resolve;
- ignores external `http(s)` links and same-page anchors;
- does not fetch external URLs.

Documentation is part of the release surface. Add a link only after the target exists.

## 6. Artifact and state checks

`npm run gate` refuses to pass unless:

1. the command runs inside a Git worktree;
2. `safeparks-brief-state.json` exists and is tracked;
3. all required release artifacts exist and are tracked;
4. both executive briefs carry the current state timestamp and content hash;
5. the state hash is stable and matches the brief metadata.

Required artifacts:

- `SAFE-PARKS-Executive-Brief.html`
- `SAFE-PARKS-Executive-Brief-2p.html`
- `SAFE-PARKS-GoNoGo-Decision.html`
- `SAFE-PARKS-Decision-Table.html`
- `SAFE-PARKS-Decision-Table.docx`
- `SAFE-PARKS-Decision-Table.xlsx`
- `SAFE-PARKS-Decision-Table-EN.tsv`
- `SAFE-PARKS-Decision-Table-TR.tsv`
- `SAFE-PARKS-Evidence-Ledger.csv`

`SAFE-PARKS-GoNoGo-Decision.pdf` is a legacy/manual PDF in the repository and is not generated by the
current build command or checked by the gate.

The state hash covers only fields used by the briefs. Tasks, audit, snapshots, KPI/budget actuals,
document metadata and risk acceptance do not invalidate the brief hash. See
[DATA-MODEL.md](DATA-MODEL.md).

## 7. Static syntax check

CI and reviewers should check every executable JavaScript file:

```bash
for f in assets/js/*.js tools/*.js tests/*.js; do
  node --check "$f"
done
```

On Windows Git Bash this is supported. Do not rely only on a browser load: a route that is not visited can
hide a syntax error.

## 8. CI workflows

### `brief-state-gate`

File: `.github/workflows/brief-state-gate.yml`

Triggers:

- pull request;
- push to `main`;
- manual `workflow_dispatch`.

Permissions: `contents: read`.

Steps:

1. checkout with full depth;
2. Node 20;
3. syntax check;
4. `npm test`;
5. `npm run check`;
6. `npm run docs:check`;
7. `node tools/ci-gate.js`.

The required check context is `brief-state-gate`. Branch protection requires it on `main`; force-push
and deletion are disabled. The repository owner can bypass as admin, but a release must not rely on that.

### `pages-health`

File: `.github/workflows/pages-health.yml`

Triggers:

- weekly schedule;
- manual dispatch.

It runs `npm run live:check` against the public URL. A failure indicates a live delivery or asset
problem, not necessarily a code bug. Inspect Pages first.

## 9. Manual browser smoke test

Run before a release or after authentication, layout, routing or state changes.

### 9.1 Gate

- [ ] Open a fresh tab at the live URL with a cache-busting query.
- [ ] The access gate is visible, shell hidden, no console errors.
- [ ] A wrong passphrase is rejected and the attempt count appears.
- [ ] The typed passphrase is not displayed.
- [ ] Sign-in succeeds with an authorised passphrase.
- [ ] The sidebar shows the expected user label.

If the passphrase is unavailable to the tester, do not claim sign-in passed. Test the gate and state
that the correct-passphrase flow was not executed.

### 9.2 Main routes

- [ ] `#dashboard` renders posture cards and management attention.
- [ ] `#project`, `#governance`, `#mandate` render.
- [ ] `#compliance` filters and status selector render.
- [ ] `#evidence` saves a reference/note and updates the missing count.
- [ ] `#risks` shows status and acceptance metadata.
- [ ] `#assurance`, `#incidents`, `#wp3`, `#deliverables`, `#docs`, `#reporting` render.
- [ ] `#gono` shows the gate decision and blocking state.
- [ ] `#management` shows tasks, decisions, actuals, metadata, snapshots and audit.
- [ ] `#settings` renders identity fields and data actions.
- [ ] Unknown hash falls back to dashboard.
- [ ] Browser console has no errors on each visited route.

### 9.3 Management

- [ ] Add a task, change its status, reload and confirm persistence.
- [ ] Save a decision status and metadata; confirm audit entries.
- [ ] Record a risk acceptance; confirm risk status and expiry.
- [ ] Save a KPI actual and a budget actual.
- [ ] Save a document version/review field.
- [ ] Create a snapshot; restore it; confirm audit/snapshots are preserved.
- [ ] Download audit CSV and task ICS; inspect headers.
- [ ] Sign out; confirm the gate returns.

### 9.4 Language, theme and print

- [ ] TR/EN switch changes labels and document language.
- [ ] Dark/light switch is readable, including logo and tables.
- [ ] Print preview hides navigation/actions and shows the content.
- [ ] Policy print and risk print produce a usable PDF.

### 9.5 Responsive

- [ ] Sidebar becomes a drawer at narrow widths.
- [ ] Management forms wrap without horizontal overflow.
- [ ] Logo scales within the auth card and sidebar.
- [ ] Wide tables remain usable via horizontal scroll.

## 10. Release procedure

### 10.1 Prepare

1. Confirm the intended version: patch for fixes, minor for features/design/content sets.
2. Update `CHANGELOG.md`.
3. Regenerate artifacts from the reviewed canonical state.
4. Review all diffs, especially data and generated artifacts.
5. Check that no sensitive material entered the diff.

### 10.2 Validate

```bash
npm test
npm run check
npm run docs:check
node --check assets/js/app.js
npm run build:artifacts
git add -A
npm run gate
```

The gate requires tracked files. It is normal to run it after `git add` and before commit.

### 10.3 Commit and tag

Use a focused message and include the version in the tag:

```bash
git commit -m "Describe the change"
git tag -a v1.1.2 -m "SAFE-PARKS CISO Portal v1.1.2"
git push origin main
git push origin v1.1.2
```

Keep `APP_VERSION`, the script/style query strings, `package.json`, the brief state `appVersion` and
release tag aligned.

### 10.4 Verify Pages

1. Inspect the Pages build for the pushed commit.
2. Wait for `built`.
3. Open the live URL with a cache-busting query.
4. Run the manual gate/route smoke checks.
5. Check new assets return 200 and the expected content type.
6. Check the CI run is green.
7. Run `npm run live:check`.

A successful build alone does not prove the page renders.

### 10.5 Announce and archive

- Record the release in `CHANGELOG.md`.
- Keep the tag.
- Confirm the backup of the canonical state and any local exports.
- Tell users what changed and whether they must clear a cached favicon.

## 11. Rollback

### Wrong content or broken release

1. Identify the last known-good commit/tag.
2. Prefer a forward fix if the defect is small and understood.
3. Otherwise revert the bad commit:
   ```bash
   git revert <commit>
   git push origin main
   ```
4. Rebuild/verify Pages.
5. If the site must be taken offline immediately, unpublish the Pages site in repository settings.
6. Restore the matching canonical state/artifact set; do not leave a tag pointing at a known-bad release.

### State corruption

- Restore the last reviewed full-state JSON.
- If the canonical state is wrong, revert its commit and rebuild the artifacts.
- Keep the corrupt export for investigation.

## 12. Release acceptance criteria

A release is acceptable only when:

- all automated checks pass;
- the required artifacts and canonical state are tracked;
- the Pages build is for the release commit;
- the live page and required assets respond;
- the access gate is present;
- the changed routes render without console errors;
- the release notes identify limits or unverified checks;
- no uncommitted working files are required for the release to work.

## 13. Known test gaps

- Correct-passphrase sign-in cannot be tested without an authorised passphrase.
- Mobile layouts are checked manually unless a browser tool is used.
- Print/PDF rendering is browser-dependent.
- External links in documentation are not fetched.
- The live check verifies availability, not visual correctness.
- CSV formula handling is a residual risk (see [SECURITY.md](SECURITY.md)).
